# Privacy Policy implementation — frontend consistency review

**Review scope:** current frontend source only, reviewed 22 October 2026. This is an implementation and source-code review, not legal advice, a production deployment audit, or confirmation that a backend, hosting provider, email provider, CDN, Vercel configuration, or third-party service complies with the published policy.

**Policy preserved on the new page:** Version `2026-08-12.v5`, effective **12 August 2026**. The policy text was not changed to resolve any of the findings below.

## Findings that require Compliance Officer / Data Protection Officer review

| Area | Current frontend evidence | Policy claim / discrepancy | Required approval or follow-up |
| --- | --- | --- | --- |
| Authentication and session cookies | `lib/api/client.ts` sends API calls with `credentials: "include"`, calls the login, refresh and logout endpoints, and reads `__Host-sf_csrf` or `sf_csrf` from `document.cookie` for the CSRF header. | Section 8 says **“Starfetch sets no cookies of its own.”** The frontend is intentionally designed to work with backend session/refresh and CSRF cookies. The frontend itself does not set these cookies, but the production Starfetch service may set them. | Confirm the live backend’s `Set-Cookie` behaviour, names, purposes, retention and attributes. Approve an updated policy/cookie disclosure or confirm an approved legal basis for the existing statement before public release. |
| Browser session storage | `lib/auth/verification-flow.ts` stores a verification ID and masked email in `sessionStorage` to continue the email-verification flow. It does not store an access token there. | Not a cookie contradiction, but this browser-side storage is not described in the supplied policy. | Decide whether the approved transparency notice should describe this short-lived verification-flow storage. |

Do not publish this claim as a description of the current implementation without approval. |

## What the source review did and did not establish

- **Authentication/session cookies:** The frontend’s request client is cookie-aware and is intended to interoperate with backend cookies. A live backend response inspection is still required to establish what is actually set in production.
- **TradingView:** No current TradingView widget/network integration was found in the reviewed public homepage source; the footer text alone is not evidence that a widget loads.
- **External market headlines:** No current external headline-feed implementation was found in the reviewed public homepage source.
- **Tracking/analytics:** No current public-page tracking script or analytics integration was found in source. This does not rule out deployment-level instrumentation.
- **Newsletter/consent:** The visible newsletter UI is local-only and does not record consent or subscribe a user.
- **Enquiries:** No public web enquiry form was found; the Footer provides email contact.
- **Forms beyond the public policy summary:** Active Individual/Joint authentication and onboarding, Corporate preview data-entry screens, authenticated portal forms, and the local-only product-interest preview exist. The policy page was intentionally not edited to add or remove any of them.

## Implementation decision

The official text has been reproduced exactly on `/privacy`, including version history and the effective date. No policy wording, version number, date, tracking code, cookie, backend endpoint, consent process, form submission, authentication behaviour, or portal workflow was changed to resolve these findings.

**Release gate recommendation:** Compliance/DPO should approve each material mismatch above, verify the deployed network/cookie behaviour, and provide a formally approved policy update if the current Version `2026-08-12.v5` is not an accurate public operational statement at release time.
